> 元歌工具箱 / 蜗牛实用工具 / 虾米工具箱 —— 三家传奇服务端工具的对比、逆向结论与性能分析

## 一、技术栈对比

| 项目 | 元歌工具箱（我们） | 蜗牛实用工具 | 虾米工具箱 |
|---|---|---|---|
| **GUI 框架** | Electron 22（Chromium + Node 16） | Electron 22 | Python 3.8 + PySide2（Qt for Python） |
| **打包方式** | Electron 便携版 + Node SEA 单文件 CLI | Electron（asar + V8 字节码） | PyInstaller（onedir，`虾米工具箱.pkg` CArchive） |
| **核心语言** | JavaScript（V8 JIT） | JavaScript（V8 字节码混淆） | Python（解释执行） |
| **安装体积** | GUI 约 150MB / CLI 93MB | 约 150MB | 约 200MB（含 python38.dll + PySide2） |
| **运行内存** | 约 150–300MB（Electron 多进程） | 约 150–300MB | 约 100–250MB（Python + Qt） |
| **启动速度** | 约 1–3s | 约 1–3s | 约 2–5s（解释器初始化慢） |
| **文件处理性能** | **快**（V8 JIT，正则/JSON/GBK 批处理强） | 快（同引擎） | **慢**（Python 解释器，大文件循环约慢 3–10 倍） |
| **授权机制** | 无（本地工具） | 授权服务器 + 机器码 | 账号登录 + 授权状态（在线） |

**结论**：三家的"壳"都是跨平台运行时套壳（Electron / Python），没有一家是原生编译。**文件处理效率：元歌(JS) ≈ 蜗牛(JS) > 虾米(Python)**。当前元歌的占用最少，性能不输任何一家。

## 三、M2 重载机制对比（详见 m2重载/ 目录）

| 实现 | 机制 | 状态 |
|---|---|---|
| **蜗牛** | Win32：FindWindow 找 M2 窗口 → GetMenu 枚举"控制-重新载入" → PostMessage WM_COMMAND 菜单点击（main 字节码含全套 FFI 调用） | 已逆向，机制与快捷助手一致 |
| **快捷助手** | VB6 + Win32：FindWindow/GetMenu/GetMenuItemID/PostMessage，16 项命令表（ReloadMonItems 等） | 已逆向，元歌已按此复刻 |
| **虾米** | UI 占位（"打开旧引擎重载项目菜单" + "重载"按钮标注"尚未接入"），无 Win32 调用；M2Server 模块仅含路径常量（NPC 可视化用） | 结论：**未实现真实重载** |

**最终实现**（元歌工具箱 `m2-reload.ps1`）：找 GameCenter/M2Server 进程 → EnumChildWindows 枚举（M2 主窗体 TfrmMain 嵌入引擎控制台"服务窗口"）→ GetMenu 找"控制-重新载入" → 匹配菜单项 → PostMessage WM_COMMAND。**已在翎风 M2 实测：怪物爆率(id=25)/所有NPC(id=20) 等 22 项全部发送成功。**

## 四、性能优化分析（要不要换 C/Rust？）

### 现状
- **瓶颈不在语言，在 GUI 框架**：三家都是套壳（Electron/Python），真正的差异是运行时开销，不是算法。
- **元歌的 CLI 已是原生级**：Node SEA 单文件，启动约 100ms，内存 <80MB，文件处理（GBK 批量、正则、MonGen 万行）毫秒级完成。

### 各语言评估（针对传奇工具这种"低频、小数据、IO 密集"场景）
| 方案 | 启动/内存 | 文件处理 | 开发成本 | 结论 |
|---|---|---|---|---|
| **Node/JS（现状）** | 快 | 快（V8 JIT） | 低 | ✅ **最合适** |
| **C/C++** | 极快 | 极快 | 极高（重写全部 UI+逻辑） | 不值得 |
| **Rust** | 极快 | 极快 | 高（无 GUI 生态，需 Tauri/egui） | 收益有限 |
| **Python（虾米）** | 慢 | 慢 | 低 | 已被证明最慢 |
| **Go** | 快 | 快 | 中（无成熟 GUI） | CLI 可以，GUI 不行 |

### 务实建议（按优先级）
1. **保持现状**：Node CLI + Electron GUI 已是三家中效率最高的组合，传奇工具操作频率低，性能感知差异可忽略。
2. **可做的微优化**（成本低收益明显）：
   - GUI 启动加 `--disable-gpu` 等参数，内存可再降 50–80MB；
   - 大文件批处理已走 CLI（SEA），GUI 只管配置与展示——架构上已分离；
   - lib.js 核心库保持纯函数、无副作用，便于未来任何语言迁移。
3. **未来如果真要原生**：只重写**核心算法层**（爆率解析/MonGen/序列化，约 2000 行）为 Rust，通过 Node N-API 调用，CLI 体验再提升但收益有限——**不建议投入**。

**一句话**：现在这套（JS 核心 + 双端交付）就是最优解，不用为了"显得厉害"去换 C/Rust，那是用 10 倍工作量换 1% 感知提升。
